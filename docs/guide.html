Cloud Spot Arbitrage

A control plane that watches live spot VM prices on Azure and AWS and moves a running Docker workload to whichever cloud is cheapest at that moment. It keeps the workload's data intact during the move and recovers automatically when a cloud takes a spot VM back.

Code: github.com/bhavishyashadani/cloud-spot-arbitrage

The 30-second pitch

Learn this paragraph and open the review with it.

Cloud providers sell their spare capacity as spot VMs, often 70–90% cheaper than normal VMs. The catch is that the price changes all the time, and the provider can take the VM back at short notice. My project treats the two clouds like two markets. It reads live spot prices from Azure and AWS every minute, and a cost model decides whether moving is worth it. If it is, a migration engine starts a VM on the cheaper cloud, which pulls my Docker image from a registry. Traffic switches over only once the new VM is healthy, and then the old VM is deleted. The application's data lives in a global database, so nothing is lost when the workload moves. If a spot VM is evicted, the system fails over by itself.

The control loop in app.py ties everything together. Every 60 seconds it runs tick():

quotes   = telemetry.collect()               # 1. fetch live prices from both clouds
evicted  = migration.check_eviction()        # 2. is our spot VM still alive?
decision = cost_model.evaluate(current, quotes, ...)   # 3. stay or move?
if autopilot and decision.action in ("bootstrap", "migrate"):
    migration.start(decision.target, reason) # 4. run the migration in a background thread

Price telemetry

A spot price on its own means little; you need a fair comparison. Every option the system considers is called a placement: a cloud, a region or zone, and a VM size. Each placement gets a key like aws:ap-southeast-2c:t3.small or azure:koreacentral:Standard_D2as_v4.

Where the prices come from

  • Azure: GET https://prices.azure.com/api/retail/prices with an OData filter for our VM size and allowed regions. The API also returns Windows, Low Priority and normal prices, so the code keeps only Linux rows whose name ends in Spot. This API needs no login.
  • AWS: ec2.describe_spot_price_history(InstanceTypes=["t3.small"], StartTime=now). This returns the current price in each availability zone (2a, 2b, 2c), which can differ from one another.

Robustness

  • If one cloud's API fails, the monitor keeps going with the last known price for that cloud, taken from the SQLite history. One flaky API can't stop the system.
  • Every reading is saved to the prices table, and the dashboard draws the chart from it.
  • Simulated price spikes are applied here. The real price is kept and shown next to the spiked one, so the demo stays honest.

Cost model

A naive system would always jump to the cheapest cloud. That would waste money, because every move has a cost: for a few minutes, two VMs run at once. It would also cause flapping, where the workload jumps back and forth whenever prices wobble. The cost model migrates only when all three of these rules pass:

RuleFormulaDefaultWhy
1. Big enough saving(current − best) / current × 100 ≥ MIN_SAVINGS_PCT10 %Ignores noise-level differences
2. Fast paybackmigration_cost / hourly_saving ≤ PAYBACK_HORIZON_H2 hThe move must pay for itself quickly
3. Cooldownnow − last_migration ≥ MIN_DWELL_MINUTES10 minPrevents flapping

The one-off migration cost is the new VM's price multiplied by the time both VMs run together: best_price × BOOT_MINUTES / 60. No data has to be copied, because the state is already in the global database, so there is no data-transfer cost.

Worked example with real prices

These are the prices the system read on 2 November 2026. You're running on AWS, and an AWS price surge (simulated ×3) hits:

QuantityValue

Without the surge, AWS costs $0.0087 and Azure $0.0218, so Azure is 150% more expensive and the model stays on AWS. That's the expected behaviour.

The model is a pure function: it takes prices and a time and returns a decision, with no network calls. That's why it can be unit-tested. tests/test_cost_model.py has 6 tests covering bootstrap, migrate, below threshold, cooldown, already cheapest, and forced migration after eviction.

Migration, step by step

This is the core of the project. The strategy is called make-before-break: the new VM is fully working before the old one is touched. If anything fails along the way, the old VM keeps serving and nothing breaks.

The four steps in the code

  1. Provision. provider.provision(candidate, name) creates the VM.
    • Azure: az vm create --priority Spot --eviction-policy Delete --max-price -1 --custom-data startup.sh, then az vm open-port 8080. --max-price -1 means "pay up to the normal price, and evict me only when capacity runs out".
    • AWS: run_instances(InstanceMarketOptions={"MarketType": "spot"}, UserData=startup.sh). If the account forbids spot (the Free plan does), it retries as on-demand.
  2. Wait for health. The VM boots and runs the startup script, which installs Docker and runs the image. The engine polls http://<ip>:8080/health every 10 s. /health only returns 200 after the container is running and it has read from Cosmos DB, so a 200 proves the whole chain works.
  3. Switch the route. One write sets active_backend = new_id. The switcher reads it on every request, so the next client request goes to the new cloud straight away. This step plays the role of updating a DNS record.
  4. Drain and delete the old VM. After a 5-second wait for in-flight requests, the old VM is terminated. On Azure, its public IP, firewall group (NSG) and virtual network are deleted too.

What if it fails?

Everything sits inside try/except. On any error, such as no capacity, a health-check timeout or an API error, the engine:

  • deletes the half-created new VM, so you're never billed for a broken one;
  • leaves the route pointing at the old VM, so clients see no change;
  • excludes the failed placement for 30 minutes, so the next control-loop tick picks the next cheapest option;
  • marks the migration as failed on the dashboard, with the exact error message.
This happened for realAzure for Students rejected spot VMs of several sizes with "SkuNotAvailable / Capacity Restrictions". The engine rolled back each time, excluded that region and tried the next. Point this out in the review: it shows the system copes with real cloud failures, not just the happy path.

Only one migration can run at a time, enforced by a threading.Lock. Every step is saved with a timestamp in the migrations table, and the dashboard displays them.

Spot eviction failover

A spot VM can be reclaimed by its cloud at any time. Every tick, the engine calls provider.status(instance_id):

  • Azure: the VM uses --eviction-policy Delete, so an evicted VM simply disappears. If az vm get-instance-view can't find it, it was evicted.
  • AWS: a state of terminated, shutting-down or stopped that we didn't cause counts as evicted.

When an eviction is detected, the engine clears the route, excludes that placement for 30 minutes, and the cost model immediately chooses the next cheapest placement. The cooldown rule doesn't apply here, because downtime costs more than flapping. The Simulate spot eviction button on the dashboard really deletes the active VM behind the system's back, so the failover you show is genuine.

Traffic switcher (the "DNS")

Clients never talk to a VM directly. They always call http://localhost:8000/app/. For each request, the switcher:

  1. reads the active backend from the database;
  2. forwards the request to http://<vm-ip>:8080/ using httpx;
  3. returns the response with an added header, X-Served-By: aws/ap-southeast-2c, so you can see which cloud answered.

Why not real DNS? DNS records are cached by resolvers for their TTL, often 60–300 s. During that time some clients would still go to the old VM after it's deleted. A proxy switches instantly. A production system would put this proxy behind a stable public DNS name, or use a global load balancer such as Cloudflare or Azure Front Door. Your GitHub Student Pack includes a free domain if a reviewer asks about real DNS.

Global datastore: why the data survives

The VMs are stateless: nothing important is stored on them. All state is in Azure Cosmos DB (free tier, Korea Central). Both the Azure VM and the AWS VM connect to the same database over the internet.

The demo state is a visit counter document:

{ "id": "counter", "visits": 42, "served_by": { "aws": 30, "azure": 12 } }

Every client request increments it. After a migration, the counter carries on from where it was, on the other cloud, and served_by shows that both clouds wrote to it. That's your proof that the state moved with the workload.

Optimistic concurrency

Two VMs run during a cutover, so two requests could update the counter at the same moment. The workload uses ETags to prevent lost updates: it reads the document with its ETag and writes back with match_condition=IfNotModified. If someone else changed the document in between, Cosmos rejects the write, and the code reads again and retries. No update is ever lost.

Docker, end to end

Docker is what makes the workload portable across clouds. The same image runs unchanged on Azure Ubuntu and AWS Amazon Linux.

1. The application: workload/app.py

A small FastAPI web app with two routes:

  • GET / increments the visit counter in Cosmos DB and returns which cloud, region and VM served the request.
  • GET /health checks that Cosmos DB is reachable and returns 200. The migration engine uses this.

The VM doesn't know which cloud it's on. That information arrives through environment variables: CLOUD, REGION, SKU, INSTANCE, COSMOS_ENDPOINT and COSMOS_KEY.

2. The Dockerfile, line by line

FROM python:3.12-slim                    # small official Python base image (Debian)
WORKDIR /app                             # all following commands run in /app
COPY requirements.txt .                  # copy the dependency list first...
RUN pip install --no-cache-dir -r requirements.txt   # ...so this layer is cached unless deps change
COPY app.py .                            # then the code (changes often, small layer)
EXPOSE 8080                              # documents the port the app listens on
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8080"]   # start the web server

Dependencies are copied before the code on purpose. Docker caches each layer, so editing app.py rebuilds only the last small layer instead of reinstalling every package.

3. Building and publishing: GitHub Actions → GHCR

.github/workflows/workload-image.yml runs on GitHub's servers whenever workload/ changes:

  1. checks out the code;
  2. logs in to ghcr.io with the repository's automatic GITHUB_TOKEN, so no password is stored anywhere;
  3. runs docker build and docker push ghcr.io/bhavishyashadani/cloud-spot-arbitrage:latest.

The image is public, so any VM on any cloud can pull it without credentials. This is the "Multi-Cloud Container Registry" from your diagram: one registry serving both clouds.

4. How a VM runs it: the startup script

When the engine creates a VM, it passes this script as Azure custom-data or AWS UserData. The VM runs it once, as root, on first boot:

#!/bin/bash
set -eux
if command -v apt-get; then apt-get install -y docker.io   # Azure: Ubuntu
else dnf install -y docker; fi                             # AWS: Amazon Linux
systemctl enable --now docker
docker run -d --restart always -p 8080:8080 \
  -e CLOUD=aws -e REGION=ap-southeast-2c -e COSMOS_ENDPOINT=... -e COSMOS_KEY=... \
  ghcr.io/bhavishyashadani/cloud-spot-arbitrage:latest     # pulls the image if not present

-p 8080:8080 maps the VM's port 8080 to the container's port 8080. The Azure NSG rule and the AWS security group both allow inbound traffic on 8080. --restart always brings the container back if it crashes or the VM reboots.

5. Showing Docker live to the reviewer (on your laptop)

Run these in the project folder with Docker Desktop open. They run the same image the clouds run, locally:

# pull the published image from the registry

Likely reviewer questions

Why not just always use the cheapest cloud?

Every migration costs money, because two VMs overlap during the switch, and it carries risk. Price differences of a few percent are noise. The three rules (savings threshold, payback time, cooldown) make sure a move is worth it and prevent flapping.

How do you avoid downtime during migration?

Make-before-break. Traffic switches only after the new VM passes its health check, which proves the image is running and the database is reachable. The old VM keeps serving until then, and is drained for 5 seconds before it's deleted.

What happens to the data?

The VMs are stateless. State lives in Cosmos DB, which both clouds can reach, so there's nothing to copy. ETag-based optimistic concurrency stops two VMs that run at the same time from overwriting each other's updates.

Why Docker?

Portability. One image runs the same on Ubuntu (Azure) and Amazon Linux (AWS). The VM only needs Docker installed, and the image is pulled from one registry that both clouds can reach.

Isn't AWS running on-demand, not spot?

Yes, because the AWS Free plan blocks spot launches through a service control policy. The code requests spot first and falls back automatically. With a paid account, the same code launches real spot instances with no change. Decisions always use real spot prices.

Why a proxy instead of real DNS?

DNS is cached for its TTL, so some clients would keep hitting the old VM after it's deleted. A proxy switches instantly. In production you'd put it behind a stable DNS name or a global load balancer.

What if the control plane itself crashes?

The workload keeps running, because the VMs and the database don't depend on it. All of its state (prices, active backend, migrations) is in SQLite, so it carries on after a restart. In production you'd run it on a small always-on VM, or as two replicas with leader election.

How do you know the spot VM was evicted?

Every 60 s the engine asks the cloud for the VM's status. A deleted (Azure) or terminated (AWS) VM that the engine didn't remove itself counts as an eviction. AWS also sends a 2-minute interruption warning through instance metadata, which would be a good future improvement.

What would you improve with more time?

Use the AWS 2-minute interruption notice and Azure Scheduled Events for earlier warning. Factor eviction-rate history into the cost model as a risk penalty. Spread across several regions for availability. Use a real global load balancer. Put Terraform in charge of the base infrastructure.
